# CLAUDE.md — Swiftlet

Cross-platform email client: .NET 11 + Avalonia 12, IMAP/SMTP (MailKit 5), SQLite + FTS5, OAuth2 (Google / Microsoft), English and Simplified Chinese UI.
This file lets Claude Code pick the project up in a fresh session; it also holds the project's progress and roadmap.

## First steps when taking over

1. Run `git log --oneline` and `git status` to see where the project stands and whether anything is uncommitted.
2. Run `dotnet build Swiftlet.slnx`, then run the tests project by project (see below). The baseline is **1808 tests** (Domain 106 / Application 140 / Infrastructure 658 / Desktop 904, the totals reported by the runner) with a 0-warning build; on Windows one Unix-only test is skipped.
3. Read "Remaining work" at the end of this file. **M5a (unified inbox + labels + server-side delete) and M5.5 (read/starred flag sync) are done.** **Account management (account settings, delete, OAuth re-sign-in), IMAP IDLE, history backfill, parallel sync and the immediate flag push are implemented.** The next step is not chosen yet; candidates are verifying against real providers or M6. Ask the user before starting. The rules feature and the local trash were cancelled by the user: do not build them.
4. Storage is split per account (see **Database** below). There are no EF migrations and no code that moves data out of an old single-file database: the local dev database `%LocalAppData%\Swiftlet\swiftlet.db` created by an earlier version must be deleted once and the accounts added again, otherwise the global store has the wrong schema. Inside an account database, `SqliteSchemaInitializer` still adds the column `Messages.IsFlagSyncPending` in place, and in the global store it adds `Accounts.HasCustomDisplayName`, `Accounts.ArchiveFolderName` and `Accounts.Color`.

## Versioning

MinVer (a `GlobalPackageReference` in `Directory.Packages.props`) sets the version of every project from the git tags; never set `<Version>` by hand. Release tags are `v1.2.3` (`MinVerTagPrefix` = `v`). Without any tag a build is `0.0.0-alpha.0.<height>` (the number of commits on top of the first one); after a tag it is the next patch, `x.y.(z+1)-alpha.0.<commits since the tag>`. Code reads it through `AppVersion` (Application): `Display` for the About page and the IMAP ID, `Full` (with the commit hash) for the startup log. `AssemblyVersion` is only `major.0.0.0`, so do not show it. A build needs git and the history: a shallow clone (for example a CI checkout without `fetch-depth: 0`) or a source archive gets a wrong version.

## Releasing

Pushing a tag `v1.2.3` runs `.github/workflows/ci.yml`: build and tests on Windows, Linux and macOS (a matrix; all three must pass), then one packaging job per platform and a GitHub release with `SHA256SUMS.txt` over all packages. A tag with a suffix (`v1.2.3-beta.1`) becomes a pre-release, which the app never offers. The installer name and the sums file are what the in-app updater relies on; do not rename them. Ask the user before pushing a tag. Running the workflow by hand (`workflow_dispatch`) builds all packages as `v0.0.0-dev.<run>` artifacts of the run and releases nothing.

The program is `Swiftlet` (`Swiftlet.exe` on Windows; `AssemblyName` of the Desktop project, so `avares://` URIs start with `avares://Swiftlet/`). The installer deletes the `Swiftlet.Desktop.*` files of 0.1.0-alpha.1.

## Dependency updates

`.github/dependabot.yml` checks the NuGet packages and the GitHub Actions every Monday. Each of the two opens at most two grouped pull requests, one for major versions (`nuget-major`, `actions-major`) and one for minor and patch versions (`nuget-minor-patch`, `actions-minor-patch`); security updates come separately. Pull request CI does not run the release job (tags only), so check an update of an action used there by hand. `SQLite3MC.PCLRaw.*` is in the groups like any other package, although it encrypts the databases: `SqliteCompatibilityTests` opens a sample database written by 2.7.1 (`tests/Swiftlet.Infrastructure.Tests/TestData`) and checks its content, search index and writing. Never regenerate that file to make the test pass; a failure means the update would lock users out of their mail. `THIRD-PARTY-NOTICES.md` lists package versions and is not updated by Dependabot.

## Architecture

```
src/Swiftlet.Domain          Entities + repository interfaces. No infrastructure dependencies.
src/Swiftlet.Application     Mediator commands/queries, MailSyncService, abstractions (IImapSession, ISecretStore, IOAuthAuthorizer, ...)
src/Swiftlet.Infrastructure  EF Core/SQLite, MailKit implementations, OAuth, keychain, AccountSyncWorker, DI registration
src/Swiftlet.Desktop         Avalonia views, ViewModels, localization, dialog service, Program (host + startup)
```

Folders inside `Swiftlet.Desktop` (the namespace follows the folder; only `App` and `Program` stay at the project root):

- `Views/` the windows, including the code-built `ConfirmWindow`; `SettingsPages/` the pages of the settings window
- `ViewModels/` add account, label manager and startup; `Contacts/` (contacts window); `Main/` (main window, tree nodes, list items), `Settings/` (settings and its "About" page, language and theme options), `Compose/`
- `Services/` abstractions the view models use (dialogs, request dispatcher, UI thread, theme) and their implementations
- `Hosting/` startup, shutdown, logging setup, single instance and close-to-tray; `Html/` mail HTML document and browser preview; `Formatting/` display text and avatars
- `Controls/`, `Converters/`, `Localization/`, `Settings/`, `Styles/`, `Assets/`, `Resources/`

Dependency direction: Desktop → Infrastructure → Application → Domain.

Key design points (understand these before changing code):

- **CQRS**: uses `Mediator` (the source-generator library, not MediatR). Commands implement `ICommand<T>`, queries implement `IQuery<T>`, handlers live in the Application layer. `AddApplication()` registers Mediator with a **Scoped** lifetime (handlers depend on scoped repositories).
- **ViewModels never use `ISender` directly**; they use `IRequestDispatcher` (`ScopedRequestDispatcher`: opens a fresh DI scope per request so long-lived ViewModels do not share a `DbContext`). It has separate overloads for commands and queries because generic inference fails on Mediator's `IRequest<T>`.
- **All external interaction in Desktop is abstracted**: `IDialogService` (windows, file pickers, opening the browser, confirmation dialogs), `IRequestDispatcher`, `ILocalizer`, `ILanguagePreferenceStore`. Tests use `FakeDispatcher` / `FakeDialogService`.
- **Sync**: `MailSyncService` fetches incrementally by UID; a UIDVALIDITY change clears that folder's cache; on first sync (no cached messages in the folder) only the newest 20 messages per folder are fetched (`MailSyncOptions.InitialFetchCount`; later syncs fetch at most `MaxMessagesPerFolderPerSync` = 200 new messages). **Parallelism**: one sync uses up to `MailSyncOptions.ConnectionsPerAccount` = 3 connections (1 = serial). Folders are queued Inbox, Sent, others, All Mail, Trash/Junk (`FolderSyncOrder`); the primary connection starts at once, additional ones (at most folders - 1) join when connected and are cancelled once the queue is empty. Repositories share one context, so **all database work and folder entity changes go through `DatabaseGate`**; only IMAP calls overlap. An additional connection that cannot be opened is a warning; one that fails on a folder stops, and the primary connection retries that folder once. **History backfill**: `BackfillWorker` (BackgroundService, up to the same number of dedicated IMAP connections per account, `BackfillConnections`; additional ones are opened when a batch first has more than one download, `ParallelDownloader` keeps one download per connection, a failing additional connection is retired and the primary one takes over its message) then downloads older mail in batches of `BackfillBatchSize` = 100 through `MailBackfillService` (`IImapSession.ListOlderAsync` lists a batch with Message-IDs from the envelope, `FetchMessagesAsync` downloads the bodies), walking back from the lowest cached UID (`IMessageRepository.GetMinUidAsync`; no stored cursor, so it resumes after a restart). Every batch runs under the account's `SyncCoordinator` lock and releases it afterwards; it **ends early when anyone waits for that lock** (`SyncCoordinator.HasWaiters`): no further downloads start, the ones running are stored and the batch reports `Progressed`. A batch checks the folder's UIDVALIDITY first and raises `AccountSynced` once per batch. **Messages are committed one by one, strictly newest UID first**, although downloads overlap (so the lowest cached UID, the resume cursor, moves down without a gap and an interrupted batch loses at most the downloads in flight, one per connection); copies from other folders are committed in runs, and each commit raises `BackfillProgressed` with the folder name and how many older messages are left (status line `Status_HistoryDownloadingFolder` in `MainWindowViewModel`). **Deduplication**: before downloading, the batch's Message-IDs are looked up in the account's other folders (`IMessageRepository.FindByMessageIdsAsync`, index `IX_Messages_MessageIdHeader`, added in place by `SqliteSchemaInitializer`); a hit is copied locally (`MailMessage.CopyToFolder`, attachment metadata included, no network) and only unknown messages are downloaded. Folder order: Inbox, Sent, other folders, then `FolderRole.AllMail` (Gmail's All Mail, from the IMAP `\All` attribute; most of it is copied), then Trash and Junk last. Search hides the All Mail row of a message that also exists in another folder (the All Mail folder view itself lists everything). Rows stay per folder (no shared-content table), so labelled mail is stored twice as text. `DownloadFullHistory` (default on, Settings window) switches the whole backfill off, All Mail included; there is no separate All Mail setting. A finished account is re-checked after 1 hour; a pass that fails with a transient error is repeated 3 times (5 s doubling), then retried after 5 minutes. A folder being emptied is skipped. Known limitation: `PullFlagsAsync` still fetches the flags of the whole cached UID range at every sync, which gets expensive once the history is downloaded (needs CONDSTORE `CHANGEDSINCE` or a throttled full reconcile; not built yet) `AccountSyncWorker` (a BackgroundService) checks every 30 seconds which accounts are due, using `MailAccount.SyncInterval`, and syncs the due accounts side by side; the Sync button does the same (`MainWindowViewModel.SyncAccountsAsync`).
- **Authentication**: `MailAuthentication.AuthenticateAsync` handles both password and XOAUTH2. OAuth uses the standard authorization code flow + PKCE + loopback redirect (`OAuthAuthorizer` + `LoopbackCallbackServer`), with no MSAL dependency. The client id comes from an environment variable or `%LocalAppData%\Swiftlet\oauth.json`. Only Microsoft has a built-in default (`OAuthClientConfiguration.BuiltInMicrosoftClientId`, the project's own public client registration, multitenant plus personal accounts, redirect `http://localhost`, not publisher verified); **no secret is embedded in the code**, and Google must still be configured. A Microsoft sign-in is an organization account when the ID token's `tid` is not the personal-account tenant; it then gets the preset "Microsoft 365" (`smtp.office365.com`), a personal account keeps `smtp-mail.outlook.com`. The servers are fixed when the account is added (re-sign-in does not change them). Whether to append a Sent copy is decided by `ProviderPresets.SavesSentCopyAutomatically(account)` from the email domain or the SMTP host.
- **Secret storage**: the platform implementation of `ISecretStore` is chosen by `PlatformSecretStore.Create`: Windows DPAPI / macOS `security` command / Linux `secret-tool`, falling back to the file-based `DataProtectionSecretStore` when none is available. Tokens are stored as JSON under the key `account:{id}:oauth`.
- **Database**: storage is split into a **global store** and **one SQLite file per account**. `GlobalDbContext` (`swiftlet.db`) holds the address book and image rule tables (see **Contacts**), `Accounts`, `Labels` and `MessageLabels` (`MessageId`, `LabelId`, `AccountId`; no foreign key to messages). `AccountDbContext` (`accounts\{accountId}.db`, created on first use by `IAccountDbContextFactory` / `AccountDbContextFactory`) holds `Folders`, `Messages`, `Attachments` and the FTS5 index. `AccountContextProvider` (scoped) hands every repository of a request the same `AccountDbContext` per account. Because messages are looked up per account, repository methods and commands keyed by a folder or message id take the owning `AccountId` first (`DeleteMessageCommand`, `SetMessageReadCommand`, `SetMessageFlaggedCommand`, `SetMessageLabelCommand`, `DownloadAttachmentQuery`, `GetMessagesQuery`, `IMessageRepository`, `IFolderRepository.GetAsync`). Cross-account views (unified inbox, label filter, search without an account) query each account database for its newest `skip+take` rows and merge by `SentAt` in memory (`MessageRepository`). `MailMessage.Labels` is not mapped by EF: `MessageRepository` loads the links from the global store after reading messages and `SaveLabelsAsync` writes them. Label links of deleted messages are removed best effort (orphan links are harmless). `AccountRepository.DeleteAsync` removes the account's label links and row, then deletes the account's database files. `SqliteSchemaInitializer` has `InitializeGlobalAsync` and `InitializeAccountAsync` (`EnsureCreated` plus hand-written FTS5 DDL and triggers); `Program` initializes the global store and every existing account database at startup. **There are no EF migrations**: after changing entities, delete the local `%LocalAppData%\Swiftlet\swiftlet.db` and the `accounts` directory during development, unless the initializer adds the change in place: it adds `Messages.IsFlagSyncPending`, `Messages.IsDeletePending`, `Messages.PendingMoveFolderId`, `Messages.AiPriority` and `Folders.EmptyThroughUid` to an existing database idempotently (`pragma_table_info` + `ALTER TABLE`) and replaces an outdated `Messages_au` trigger (see **Database size**). All time fields are stored as Unix milliseconds (`UnixMillisecondsConverter`) so they sort correctly.
- **Local data protection**: all databases are **encrypted by default** with SQLite3 Multiple Ciphers (`SQLite3MC.PCLRaw.bundle`, 2.7.1 or later, because 2.6.x could silently decrypt wrong data; `Microsoft.EntityFrameworkCore.Sqlite.Core`; never add a second SQLite native bundle), ChaCha20-Poly1305 with a raw key (`Password=raw:<64 hex>`). One random key for all databases lives in `ISecretStore`; every created key gets a new entry `database:key:<id>` and `database.key-name` in the data directory lists the names (current one last), so a key is never overwritten (`DatabaseKeyProvider`; `WindowsSecretStore` writes durably through a temporary file). Without a system keychain (`DataProtectionSecretStore` fallback) nothing is encrypted. It protects database files that leave the machine or user, not against programs running as the same user. Code is in `Infrastructure/Persistence/Encryption`: `DatabaseProtection` (singleton, `IDatabaseProtection` + `IDatabaseConnectionStrings`) probes every file by reading it (`DatabaseProbe`), creates the key only when no database is unreadable, converts plain databases in place (`DatabaseEncryptionMigrator`: free space 2x the size, leave WAL, `PRAGMA rekey`, `quick_check`; an interrupted run is rolled back by SQLite's journal) under the lock file `encryption.lock`, and hands out every connection string (never log one; it holds the key). Asking for a connection string before preparation throws. Problems: failed conversion (retry / continue unencrypted for this run), keychain unavailable, busy, database error (retry), no keychain found at process start in front of encrypted data (quit and restart only, because the store is chosen once), key lost or one account database unreadable (retry / reset). A reset renames files to `*.unreadable-<time>` (nothing is deleted) and creates a new key only when the current one is missing or damaged (the old entry stays); losing the key loses the account list and labels, which live in the global store. At startup `AppStartup.TryStartQuietlyAsync` prepares behind the splash screen (see **Splash screen**) when nothing is pending; otherwise `StartupWindow` / `StartupViewModel` takes over and the host starts only afterwards. The Settings window shows the status. **Older app versions cannot open an encrypted database**, and a data directory copied to another user or computer cannot be opened. Plain text deleted during conversion may remain in free disk space. `Program` also calls `DataDirectoryProtection.RestrictToCurrentUser` at startup (Unix: the data directory becomes 0700; Windows: nothing; a refusal is only a logged warning). "View in browser" writes plain-text HTML through `HtmlPreviewStore` into a per-run directory `swiftlet-preview-*` under the system temp directory (0700 on Unix), deleted on exit; startup removes leftovers and the loose `swiftlet-<32 hex>.html` files of earlier versions. Logs, `settings.json`, previews and saved attachments are not encrypted. Master password, key rotation and an off switch were deliberately not built.
- **Splash screen**: `App` shows `Views/SplashWindow` (borderless, centered, in the taskbar, not closable by the user) as the first window and runs `TryStartQuietlyAsync` through `Hosting/SplashStartup` on the thread pool, for at least 1 s (`App.MinimumSplashDuration`, side by side with the work). The progress bar is indeterminate; `SplashViewModel` names the step (`StartupProgress`: checking the data, opening the shared database, each account database as n of m without its address, starting services, loading the main window). The main window or `StartupWindow` takes over **before** the splash closes. A hidden start (`StartMinimized`) has no splash and no minimum duration: the lifetime uses `OnExplicitShutdown` while preparing, and activation requests wait in `SingleInstance` until a window exists. A failed start logs a critical error and exits with code 1. It appears only after the runtime, the host and Avalonia are loaded.
- **Database size**: `Messages.BodyHtml` is stored compressed (`CompressedHtmlConverter` / `HtmlBodyCodec`: bytes `0xFF 0x01` + raw Deflate of the UTF-8, or the plain UTF-8 when that is not smaller; `0xFF` never occurs in UTF-8, so plain-text rows of earlier versions still read). Never query `BodyHtml` in SQL/LINQ, and an older app version cannot read compressed rows. `BodyText` stays plain text (FTS and the `LIKE` fallback read it). The FTS trigger `Messages_au` fires only on `UPDATE OF Subject, FromName, FromAddress, BodyText`, so flag changes do not re-index. `DatabaseMaintenanceWorker` (first pass 1 minute after start, then every 6 hours; never at startup or shutdown) runs `AccountDatabaseMaintenance` per account under the `SyncCoordinator` lock: leftover plain-text HTML is compressed in batches of 100 (one lock per batch), then, when pending or when free pages exceed 25% **and** 10 MB, it does FTS `rebuild` → `VACUUM` → FTS `integrity-check` (rank 1; rebuild again on mismatch, because `Messages` has no integer primary key and VACUUM may renumber the rowids the external-content index uses) → `wal_checkpoint(TRUNCATE)`. Pending work is a bit set in `PRAGMA user_version` (`AccountDatabaseTasks`: 1 compress, 2 compact); replacing the old trigger sets both, so an upgraded database is compressed and compacted once, and an interrupted run is repeated. Cancellation calls `sqlite3_interrupt`; the busy wait is 5 seconds. Measured on copies of a developer database: 93.9 MB to 17.0 MB in about 2.4 s, with identical bodies and sample search results. Known limitation: removing an account while its database is being maintained can fail to delete the files (same as during a sync).
- **Search**: FTS5 trigram tokenizer; terms shorter than 3 characters fall back to `LIKE`; query terms are escaped into literals so user input is never treated as FTS syntax. Conditions are a `MessageSearchCriteria` (Domain; all set ones must match, empty criteria match nothing): free text (subject, sender, body), sender (name or address), recipients, subject, sent range (`SentFrom` inclusive, `SentBefore` exclusive), attachments, unread, starred, plus account / folder as the scope. Sender and subject terms go into the same `MATCH` with column filters; recipients always use `LIKE` (not indexed; `Recipients` holds To and Cc **addresses only**, so display names and Bcc are never found, which was chosen to avoid a schema change). A folder search does not hide All Mail duplicates. Logs name the conditions used, never their values. UI: the filter toggle beside the search box expands `MainWindowViewModel.Filter` (`SearchFilterViewModel`): days are local whole days, the scope defaults to the selected account (all accounts for the unified inbox and labels), a dot on the toggle shows hidden active conditions, selecting another node resets everything but the expanded state, and a start date after the end date searches nothing. Paging and reloads use the criteria snapshot of the shown search; the next page of an unread or starred search skips only the listed messages that still match.
- **Attachments**: only metadata is stored locally (including `Ordinal`, the attachment's position in the server message); content is fetched from IMAP on demand via `DownloadAttachmentQuery`. Attachments are enumerated by `MimeAttachments.Enumerate` (used by both the mapper and the download, so ordinals agree): MimeKit's `Attachments` first (unchanged order), then non-text parts with a file name that are shown inline (for example a photo referenced by `cid:`). Cached messages synced before this are not backfilled.
- **Local state**: deleting and moving are queued locally and written back to the server in the background right away. Read and starred state are applied locally at once, marked per message with `MailMessage.IsFlagSyncPending`, and written to the server in the background right away (see **Immediate flag push**); the next sync writes whatever that push could not. Labels are still local only.
- **Flag sync** (M5.5): per folder, after the UIDVALIDITY check (an invalidated folder skips both push and pull), the order is push → fetch new → pull. Push: pending messages are read as untracked `MessageFlagState` projections and sent with `IImapSession.SetFlagsAsync` (only `\Seen`/`\Flagged`; clearing is pushed too); `ClearFlagSyncPendingAsync` then clears the marker only for rows whose IsRead/IsFlagged still equal the pushed values, so a change made during the push stays pending. A failed push is a logged warning, non-fatal, and the messages stay pending, so it never blocks new mail. Pull: `IImapSession.FetchFlagsAsync(folder, minUid)` for UIDs >= the lowest cached UID; the server wins except for pending messages (the guarded `ApplyServerFlagsAsync` update skips them). Cached messages absent from the result or flagged `\Deleted` are removed locally only when `RemoveServerDeletedMessages` is on (the default) and the folder was not just invalidated; an empty result for a non-empty cache is confirmed with a UID SEARCH (`ListUidsBetweenAsync`) first, so an emptied server folder is emptied locally while a search that still finds messages logs a warning and removes nothing. The pull uses untracked projections and `ExecuteUpdate`, never tracked message entities.
- **Folder check on open**: selecting a folder node sends `SyncFolderCommand` off the UI thread (`MainWindowViewModel.CheckFolderIfDue`, at most once per folder per 30 s), which runs `MailSyncService.SyncSingleFolderAsync` (the same per-folder steps as an account sync, on one new connection) under the `SyncCoordinator` account lock and raises `AccountSynced` only if the cache changed; failures are only logged. It exists because only the INBOX has IDLE: other folders would otherwise show server-side deletions only after the next timed sync. The unified inbox and label views do not trigger it.
- **Sent copy**: after SMTP delivery `MailKitMailSender` appends a copy to the server's Sent folder unless the provider stores one itself (`SavesSentCopyAutomatically`). `AppendToSentAsync` tries MailKit's special folder first and falls back to the folder listing (`SentFolderLocator`: the first selectable folder with `FolderRole.Sent`, the rule the tree uses; no guessing by name), because iCloud failed the MailKit lookup although its listing yields a Sent role. A failed or impossible append is only a logged warning. After every delivered message `SendMessageCommand` raises `ISyncEvents.MessageSent`, and `MainWindowViewModel` checks that account's cached Sent folder at once, ignoring the 30 s throttle; there is no retry if a provider saves its own copy late.
- **Immediate flag push**: `SetMessageReadCommand` / `SetMessageFlaggedCommand` notify `FlagPushSignal` after saving. `FlagPushWorker` runs one loop per account: it waits 300 ms for further changes, then `PendingFlagService.PushFolderAsync` writes every folder with pending rows (UIDVALIDITY check, STORE, clear the matching marks). The connection is kept for 2 minutes after the last change; a push that fails on a kept connection reconnects at once, passing errors are retried 3 times, and after that the rows stay pending for the next sync. It does **not** take the `SyncCoordinator` account lock, so it does not wait for a running sync. Instead `FlagCoordinator` (per folder) is held by the push, by the sync around UIDVALIDITY invalidation + push, and around the flag pull, so flags read before a push are never applied after it.
- **Tray and single instance**: with `CloseToTray` on (default, Settings window, key `closeToTray`) the close button hides the main window and sync, IDLE and the 30 s refresh keep running; `Hosting/CloseToTray` cancels only a user close (`WindowClosingEventArgs.CloseReason == WindowClosing`, not programmatic), so quitting and the system session ending go through. `Opened` fires again on every `Show()`, so `MainWindow` unsubscribes after the first one, and a hidden window is never used as a dialog owner. `App` creates the tray icon (`Services/AvaloniaTrayIcon`, Avalonia `TrayIcon` + `NativeMenu`) together with the main window, not for the startup window; its texts and commands are in `ViewModels/TrayViewModel` (Open, Compose and Settings without showing the main window, Sync all accounts, Quit = `desktop.Shutdown()`). The settings window is a dialog of the main window when that is on screen and a standalone window otherwise; a second request brings the open one to the front. The tooltip (`Formatting/TraySummary`, at most 127 characters, the Windows limit) lists the unread total and the unread inbox count per account (downloaded mail only), updated through `MainWindowViewModel.UnreadChanged`. `Hosting/SingleInstance` allows one instance per data directory: the lock file `instance.lock` (`FileShare.None`) plus a named pipe; a later start sends an activation request (passing on the Windows foreground right) and exits, retrying for 10 s while the other instance starts or quits. `Program` acquires it before anything else, stops listening when the window loop ends and releases the lock after the host stopped. The macOS Dock reopen event also shows the window. **Hidden start**: the setting `StartMinimized` (key `startMinimized`, default off, independent of `CloseToTray`) keeps the main window hidden at startup (tray only): `App.AdoptMain` then leaves `desktop.MainWindow` unset (the framework would show it), uses `OnExplicitShutdown`, ends the app when the window closes and assigns `MainWindow` on its first `Opened`; it applies to the startup-window path too. There is no detection of a missing system tray (default GNOME): starting the app again brings the window back.
- **Attachment hover preview**: resting the pointer on an attachment button for 500 ms (`Hosting/AttachmentHoverController`; the window tracks `PointerMoved` and finds the button under the pointer, because the buttons live in a data template; leaving the button, a press, deactivating or closing the window hides it) shows `Views/AttachmentPreviewWindow` through `Services/AvaloniaAttachmentPreviewPresenter` (`IAttachmentPreviewPresenter`). It is a separate borderless, topmost, non-activating window like `NewMailWindow`, because the attachment strip sits right above the native web view, which would cover a Popup or ToolTip; it is placed below the button (above when there is no room, `AttachmentPreviewWindow.Place`) and never takes the pointer, so moving onto it hides it. `MainWindowViewModel.LoadAttachmentPreviewAsync` sends `GetAttachmentPreviewQuery`; a failure is only logged (no status line error) and shows "No preview available". The handler (Application) answers from `AttachmentPreviewCache` (singleton LRU, 20 entries / 20 MB, only successful previews), refuses by the stored `Size` above 10 MB (`TooLarge`) and by `IAttachmentPreviewer.CanPreview` (file name and content type, so an unsupported type costs no connection) before it downloads the attachment (`IImapSession.DownloadAttachmentAsync`, one connection and the whole message per first hover). `Infrastructure/Mail/AttachmentPreviewer` builds: image thumbnails (longest side 480, Magick.NET: png/jpg/gif/bmp/webp/tiff/heic/ico/psd/svg/tga/avif, refused above 100 million pixels, PNG when it has alpha, else JPEG), text (first 8 KB / 40 lines / 2000 characters through `MimeTextDecoder`, so GBK etc. work; a NUL byte means binary; common text, code and config extensions, `.eml`), a zip entry list (first 30), and the text of docx / xlsx / pptx (first 800 characters, XML read with DTD prohibited and stopped early). - **Account management**: right-clicking an account node in the tree opens a context menu (no prior selection needed; the commands take the node as parameter) with "Remove account" and, for OAuth accounts only (`AccountNodeViewModel.CanReauthenticate`), "Re-sign in". `DeleteAccountCommand` deletes the local rows first (account, folders, messages and their label links; the account row is the point of no return) and only then the secrets (password / OAuth tokens); the mailbox on the server is never touched, which the confirmation dialog states (Cancel is the default). `ReloadAccountsAsync` removes tree nodes of accounts that no longer exist, repairs a selection that pointed into them, and never re-inserts a node for an account that a newer reload already dropped. After a delete attempt (even a failed one) the view model reloads the tree from the database and re-runs the active search or reloads the folder view. `DeleteAccountCommand` removes both secret keys (password and OAuth) even when the account row is already gone, so a retry after a failed secret removal cleans up. `AccountSyncWorker` uses one DI scope (one `DbContext`) per account, so a failed sync of one account (for example one deleted mid-sync) cannot leave stale tracked entities that break the next account. `ReauthenticateOAuthAccountCommand` (OAuth accounts only) runs the browser sign-in, rejects a different email address (case-insensitive compare) before touching stored tokens, re-checks that the account still exists after the browser step, saves the new tokens, verifies them with an IMAP connection and restores the tokens that were stored just before the overwrite if that fails (a restore failure is logged and attached to the original exception); the view model then syncs the account. `AddAccountCommand` allows concurrent execution, so the toolbar button stays enabled during the first sync of a newly added account; `IsBusy` is counted (`BeginBusy` / `EndBusy`) because syncs can overlap. - **Account settings**: the account context menu starts with "Account settings…" (`EditAccountWindow` / `EditAccountViewModel`, `IDialogService.ShowEditAccountAsync`). `UpdateAccountCommand` changes the display name and sync interval (any account) and the password and IMAP / SMTP endpoints (password accounts only; the address cannot be changed). A blank name removes a typed name (`MailAccount.ChangeDisplayName`: falls back to the local part) and keeps a filled-in one. Only a changed IMAP endpoint or password is verified with an IMAP sign-in (`IImapSessionFactory.ConnectAsync(account, password)` tries a new password without storing it); SMTP is not verified, and name / interval changes save offline. The password is stored only after verification and restored if saving the row fails. A changed IMAP endpoint or password bumps `AccountConnectionRevisions` (singleton, in memory): `InboxWatcher` restarts the account's loop at its next 30 s reconcile (also re-checking a server without IDLE), `BackfillWorker` ends the running pass before its next batch and lifts its pause, `DeletionWorker` replaces its connection before the next batch (checked under the account lock) and lifts a block, `FlagPushWorker` drops its kept connection before the next push. Read the revision **before** reading the account. The desktop then reloads the tree (`AccountNodeViewModel.Update`) and syncs the account if the connection changed. The cached mail is kept when the server changes (a different UIDVALIDITY clears a folder as usual). Known limitations: a sync already running finishes with the old settings, and a deletion run waiting between retries sees new settings only at its next attempt (up to 5 minutes).
- **IDLE / push**: `InboxWatcher` (a BackgroundService in Infrastructure) keeps one dedicated IMAP connection per account in IDLE on the INBOX, separate from the sync connections. The first wait of every session reports a change (`FolderChangeTracker.Observe` returns true for the first observation of a folder), so every (re)connect is followed by a sync, and the wait after that sync is compared against the baseline taken before it; mail that arrives during the sync is therefore caught by the next wait. `FolderChangeTracker` covers changes between waits, and the IDLE events cover changes during a wait. After an IDLE the baseline is recorded with UIDNEXT unknown (MailKit refreshes it only on SELECT), so the next comparison uses the message count only. Known limitation: a UIDNEXT-only change right after an IDLE (for example mail arrives and another client moves one out of the INBOX during the post-IDLE sync) is not detected by the tracker at all; only a later IDLE event or the polling timer recovers it (the 5-minute renewal does not sync). The reconnect backoff resets only after a wait that actually idled, not after the first wait of a session (which returns right after the SELECT), so an IDLE that fails on every connection keeps backing off. Each IDLE wait lasts at most 5 minutes (`maxWait`), after which it renews; a dropped connection is retried with a backoff of 5 seconds doubling up to 5 minutes, and an account that needs OAuth re-sign-in waits 5 minutes before the next attempt. `SyncCoordinator` serializes syncs per account, so the IDLE-triggered sync, the timer sync and the Sync button never overlap for one account. `SyncAccountCommandHandler` raises `ISyncEvents.AccountSynced` (a singleton, possibly on a background thread) after every successful sync, **and once earlier as soon as the INBOX is done** if something in it changed and the account has further folders (`MailSyncService.SyncAsync` callback; the final event reports only the messages not announced yet); `MainWindowViewModel` subscribes, marshals to the UI thread through `IUiThread` (`AvaloniaUiThread` in production) and refreshes coalesced: refreshes never overlap, and syncs arriving during a refresh cause at most one follow-up. The subscription ends when `MainWindow` closes (`Dispose`). The 30-second UI timer and the `AccountSyncWorker` timer stay as fallbacks, and servers without the IDLE capability are served by timer polling alone.
- **Server-side delete** (background): the UI only queues. `DeleteMessagesCommand` marks rows `MailMessage.IsDeletePending` (hidden from every view query, still counted by `GetMin/MaxUidAsync` so they are not downloaded again) and notifies `DeletionSignal`. `EmptyFolderCommand` (folder context menu "Delete all messages", never for All Mail) stores `MailFolder.EmptyThroughUid` = highest cached UID, so the whole server folder including undownloaded history is deleted but later mail is kept; a UIDVALIDITY change clears the request. Both columns are added in place by `SqliteSchemaInitializer`. `DeletionWorker` (signal, plus a 30 s poll for work left from the last run) runs at most one run per account, one pass on one connection; a signal or poll that finds the account running asks that run for another pass, so work added while a run is ending is not left to the next poll; `PendingDeletionService.ProcessBatchAsync` handles one folder and at most 100 messages per `SyncCoordinator` lock: UIDVALIDITY check, then `IImapSession.DeleteMessagesAsync` (one MOVE to Trash, or `\Deleted` + UID EXPUNGE inside Trash / without a Trash folder, which needs UIDPLUS); local rows change only after the server confirmed. Before a **move** (not a permanent delete or an emptied folder) the batch's pending read / starred changes are written, under the folder's `FlagCoordinator` lock that also covers the move and the cache update, so a moved message keeps them and the immediate push never writes to the old UID; a refused flag write is only a warning (the rows stay pending), other errors repeat the whole batch. Emptying lists server UIDs with `ListUidsBetweenAsync` and walks them oldest first, so the highest cached UID stays until the end. Transient errors retry forever (5 s doubling to 5 min); `MailOperationRejectedException` (MailKit `ImapCommandException` / `FolderNotFoundException`) and `NotSupportedException` clear the marks so the messages reappear; other errors (sign-in) pause the account 5 minutes. Progress is raised as `ISyncEvents.DeletionProgressed`. The list is multi-select (Delete key, context menu); one confirmation per action (Cancel default), then the rows leave the list at once. **Moving to Trash keeps the cached row** (same id, labels, attachments; `IMessageRepository.MoveToFolderAsync`) when the server reports the new UID, the cached Trash has the server's UIDVALIDITY and every server message between its highest cached UID and the new one is a row being moved (no hole, which the incremental sync would never fill); otherwise the row is deleted and the sync fetches it from Trash. Other folders' copies of the same message (Gmail) stay until the next sync/pull.
- **Moving between folders** (same account only) reuses the whole delete pipeline; the class names (`PendingDeletionService`, `DeletionWorker`, `DeletionSignal`, `IsDeletePending`) kept their delete wording. `MoveMessagesCommand` checks that the target belongs to the account and `MarkMovePendingAsync` sets `IsDeletePending` plus `MailMessage.PendingMoveFolderId` (skipping rows already in the target or already pending); a later delete or empty-folder request clears the target, so **deletion always wins**. A batch has one (source folder, destination) pair, a target also applies to moves out of Trash, a target folder that no longer exists counts as refused, and a refused move restores only the moves to that target. The row is re-homed into the destination under the same rules as a move to Trash. In the UI the message context menu has a "Move to" submenu (no confirmation, because moving back undoes it), disabled for a selection spanning accounts; `MoveTargets` is filled **only when the menu opens** (`RefreshMoveTargets`), because removing the entries while one is being clicked kept the menu open. Known limitations: when the row cannot be re-homed (destination never synchronized or a hole), the message shows only after the destination's next sync (opening the folder triggers one); an older app version treats a still pending move as a deletion (permanent for a move out of Trash).
- **Archive**: "Archive" (message context menu and reading pane button, `MainWindowViewModel.ArchiveSelectedCommand`) is a move: it sends one `MoveMessagesCommand` per account and has no background logic of its own. The target comes from `ArchiveFolderResolver` (Application): `MailAccount.ArchiveFolderName` (the folder full name, chosen in the account settings; null = automatic), else the folder with `FolderRole.Archive`, else `FolderRole.AllMail` (Gmail: leaves the inbox). A chosen folder that is not cached is **never** replaced by another one; archiving that account is disabled instead. A selection may span accounts; messages already in the target or without one stay, and the command is enabled if any message can be archived. No confirmation, no keyboard shortcut. The account settings list every folder except Inbox, Drafts, Junk and Trash, and keep a saved folder that no longer exists (marked as not found).
- **Retries** use Polly (`Polly.Core`, Infrastructure only), all defined in `Infrastructure/Resilience`: `TransientErrors` (network, timeouts, MailKit connection/protocol errors, HTTP 5xx/408/429; never authentication failures) and `RetryPipelines` (`Endless` for the deletion worker and the IDLE watcher, with a `FailureStreak` reset on success and 5 minutes for an expired sign-in; `Transient` for the limited retries). Account sync repeats twice (5 s, 10 s), backfill 3 times, OAuth token **refresh** 3 times (1 s doubling). Deliberately no automatic retry: SMTP send and Sent append (duplicates), the authorization-code exchange, the Sync button, interactive account operations, attachment downloads. The IDLE watcher retries every failure, not only transient ones.
- **Shutdown**: after the window closes, `Program` calls `HostShutdown.Stop`, which stops the host on the thread pool. The main thread still carries Avalonia's synchronization context but no longer pumps messages, so awaiting there made `StopAsync` hang until the host's 30 s timeout. `ConfigureHostShutdown` stops the hosted services concurrently with a 5 s timeout (abandoned work is safe: transactions are atomic, pending marks are stored). IMAP disposal waits at most 2 s for LOGOUT. Nothing compacts the database on exit; SQLite only checkpoints the WAL when the pooled connections close.
- **Mail text encoding**: `MailEncodings.Register()` (called from `Program` and from `MimeTextDecoder`'s static constructor) registers the code pages provider so GBK / GB2312 / Big5 / Windows-125x work. It must run before the first use of MimeKit: MimeKit resolves gb2312 / gbk / big5 / gb18030 when its charset cache is initialized and keeps a failed lookup for the lifetime of the process, so RFC 2047 headers then decode as Latin-1 (the static constructor of `MimeTextDecoder` is too late for that). `Program.Main` registers first; the Infrastructure tests do so in a module initializer (`TestModuleInitializer`). `MimeMessageMapper` does not trust MimeKit's `TextBody` / `HtmlBody`: `MimeTextDecoder` decodes the part's bytes itself. A reliable declared charset is used unless the bytes are valid UTF-8 with at least two non-ASCII characters (then UTF-8 wins); undeclared, unknown or commonly mislabelled charsets (us-ascii, iso-8859-1, windows-1252) are guessed in the order UTF-8, GB18030, Big5 (Big5 text that is also valid GB18030 is read as GB18030; this is a known limitation without a detection library); HTML without a MIME charset uses its `<meta charset>`; undeclared ISO-2022-JP is recognised by its escape sequence. Raw 8-bit Subject / From headers (no RFC 2047 encoding) are decoded by the same guessing; RFC 2047 encoded words are left to MimeKit. Already cached messages are not re-decoded.
- **HTML mail rendering**: the reading pane shows `MessageItemViewModel.HtmlDocument` (built by `HtmlMailDocument`: UTF-8 meta, CSP `default-src 'none'; img-src data:; style-src 'unsafe-inline'`, white base style) in `HtmlBodyView`, a `Border` hosting Avalonia's `NativeWebView` (package `Avalonia.Controls.WebView`, MIT, WebView2 on Windows). The document is loaded once `AdapterCreated` fires; navigations to http/https/mailto links are cancelled and opened with `TopLevel.Launcher`, new-window requests are swallowed, so scripts and remote images never run. Messages without HTML keep the plain-text `SelectableTextBlock`; the toolbar "view in browser" button still exists. **Images**: remote (http/https) images are blocked by the CSP by default; when the HTML references some (`HtmlMailDocument.HasRemoteImages`) the pane shows a banner with a "Load images" button, which sets `MessageItemViewModel.AllowRemoteImages` for that message object only (not persisted) and rebuilds the document with `img-src data: https: http:` (scripts and everything else stay blocked). Images embedded in the message (`cid:`) are not stored locally: selecting a message whose HTML has `cid:` references (`InlineImageReferences.Find`) sends `GetInlineImagesQuery` once per message (`InlineImagesRequested`; a failure shows a status error and the next selection retries), which connects to IMAP only when there are references, and `InlineImageExtractor` takes png/jpeg/gif/webp/bmp parts matched by normalized Content-ID (no SVG, 10 MB per message). HEIC / HEIF parts, which the web view cannot display, and images over 2 MB (phone photos, up to 25 MB source; large GIFs are skipped) are converted to a JPEG with a side of at most 2048 px by `HeicConverter` (Magick.NET); undecodable ones are left out. Remote HEIC images are not converted. `HtmlMailDocument.Build` replaces `cid:` references with `data:` URIs. **Saved allow rules**: the banner's `SplitButton` offers "Load images" (this message only) plus "always for this sender address" / "always for this sender's domain" (`MessageItemViewModel.AlwaysAllowSenderCommand` / `AlwaysAllowDomainCommand`, saved through `MainWindowViewModel.RememberRemoteImagesAsync`). Rules are lowercase strings: with `@` an exact address rule, otherwise a domain rule that matches the domain and its subdomains (`RemoteImageRule.TryNormalize` / `Candidates` in Application). They live in the global store's table `RemoteImageRules` (`Rule`, `AddedAt`; created by `SqliteSchemaInitializer.InitializeGlobalAsync` with `CREATE TABLE IF NOT EXISTS`, so an existing `swiftlet.db` is upgraded in place) and `RemoteImageRuleStore` (singleton `IRemoteImageRules`) keeps a sorted in-memory copy loaded at startup (`Program`), so `IsAllowed(From)` on selection is a synchronous lookup with no banner flash; writes go to the database first, then memory. The Settings window lists, searches (first 200 shown, with a count), adds and removes rules. The From header can be forged, so a rule only controls privacy (the sender learning the mail was opened), never security.
- **AI settings and clients** (all AI actions are triggered by the user only): the Settings page "AI" (`AiPage` / `AiSettingsViewModel`, saves only with its button) edits `AiConfiguration` (`IAiSettings`, implemented by `AppSettings`, key `ai` in `settings.json`; `AddApplication()` registers a disabled default with `TryAdd`). Off by default. `IsReady` requires the saved `ConfirmedDestination` (provider + scheme/host/port) to match the address, and saving an enabled new destination asks the user first. Addresses must be https, or http on loopback (`AiEndpoint`). API keys live in the secret store only (`ai:apikey:{provider}`, `AiKeyStore`), bound to the destination they were typed for. Use cases talk to `Microsoft.Extensions.AI.IChatClient` from `IAiClientFactory`; the Infrastructure `AiClientFactory` builds the official `Anthropic` client (`claude-opus-5-5` by default) or the `OpenAI` client for compatible services, with no retries, no redirects, a 5 minute timeout and explicit settings so SDK environment variables cannot redirect content or add credentials (the factory removes `ANTHROPIC_CUSTOM_HEADERS` from the process, because the SDK caches it once and an `Authorization` entry makes every request fail before it is sent; `ClaudeHeaderHandler` sends the key as `x-api-key` only). `TranslatingChatClient` turns every SDK failure into `AiException` **without** the inner exception or response body, because those can echo mail content into the log. Never log prompts, answers or keys. Mail is untrusted input: no model tools, plain-text output, every write confirmed by the user.
- **AI summary and translation**: the reading pane buttons (shown only while `AiConfiguration.IsReady`) open `Views/AiPanel` (`ViewModels/Ai/AiAssistViewModel`, singleton, `MainWindowViewModel.AiAssist`) **in the layout above the mail body**, with radio buttons for the answer language (default: UI language), because popups and drop-downs would open over the native web view. Selecting another message cancels and closes it; a refresh of the same message keeps it. `SummarizeMessageQuery` / `TranslateMessageQuery` are Mediator `IStreamQuery<AiOutput>` (`IRequestDispatcher.StreamAsync` keeps the scope for the enumeration; `StreamLoggingBehavior` logs them, since `LoggingBehavior` does not see streams). `AiAnswers` is the one way to the service (apart from the connection test): `RequireTarget` checks `IsReady`, and it streams with the output limit, reasoning filter and refusal handling. `AiMessageService` sends what `AiContentBuilder` builds (subject, sender, date, plain body cut at `MaxInputCharacters`, between a random delimiter the prompt declares as data), drops a leading `<think>` block (`ThinkTagFilter`), reports truncation and refusal, and keeps complete answers in memory only (`AiResultCache`, 20 entries, keyed by message, task, language and settings). Claude gets `MaxOutputTokens` 16000; compatible services none, because many reject large limits. The Anthropic server-side refusal fallback (beta) is not used.
- **AI writing help**: the compose window has a "Writing help" button only when AI was ready as the window opened (`ComposeViewModel.Assist`, `ComposeAssistViewModel`, `Views/ComposeAiPanel` below the message; the window raises its minimum height to 620 while the panel is open). `RewriteTextQuery` (polish, formal, concise, friendly, proofread, to English / Chinese) sends only the user's own text, split from the quote by `ComposeBodyParts` (the quote the template put in, else its first line, else the first `>` line and the attribution above it; everything from there on is left alone). `DraftReplyQuery` (replies only) sends the replied mail and the typed notes. Text of the user above `MaxInputCharacters` is refused (`AiFailure.TooLong`), never cut, because the answer may replace it. The answer is only previewed: Replace (refused when the own text changed since asking) or Insert above, both disabled for a stopped, cut-off or refused answer. Nothing is sent or changed without a click.
- **AI classification and priority**: the message context menu has "Classify with AI…" (only while AI is ready) opening `Views/ClassifyWindow` (`ClassifyViewModel`, modal). `ClassifyMessagesQuery` (stream, first 20 messages) sends **one request per message** (2 at a time, body cut at 4000 characters or the lower input limit, label names as JSON in the instructions), so one mail cannot influence another; database reads happen before the requests start. `ClassificationParser` takes the JSON out of any text (no `json_schema`, many compatible services lack it) and lets only existing labels and High / Normal / Low through; only changes are suggested (no priority equals Normal). Rejected / timeout / unavailable fail that message only; other failures end the request. Suggestions are ticked and nothing is saved until "Apply" (`SetMessageLabelCommand`, `SetMessagePriorityCommand`). The priority is `MailMessage.AiPriority` (nullable, local only, stored values 1 High / 2 Normal / 3 Low; column added in place by `SqliteSchemaInitializer`, ignored by older versions); rows mark High and Low, "Clear priority" works without AI. It survives a local re-homing on move, but not a re-download, and is not copied to other folders' rows of the same mail.
- **Logging**: Serilog (`Serilog.Extensions.Hosting` + `Serilog.Sinks.File`), configured in `Desktop/Hosting/LogSetup.cs`: files `%LocalAppData%\Swiftlet\logs\swiftlet-YYYYMMDD[_NNN].log`, rolled daily and when a file passes 10 MB, at most 7 files kept; level Debug for `Swiftlet.*`, Information otherwise, `Microsoft.*` at Warning. Code logs through `ILogger<T>`. `LoggingBehavior` (Mediator pipeline, registered in `AddApplication`) logs every command (Information) and query (Debug) with its type name and duration, and failures as errors; it never writes the request contents (passwords, bodies). **Every line about a mailbox is tagged** `[email] [folder]` through logging scopes (`ILogger.BeginMailScope`, `Application/Logging`), printed by the output template in `LogSetup`: `LoggingBehavior` opens one for requests implementing `IAccountRequest` / `IFolderRequest` (so everything the handler logs inherits it), and the sync, backfill, IDLE, deletion, flag push and maintenance code opens its own; new work outside a request needs one too. A request adds details to its line only through `ILogDetails.DescribeForLog` (identifiers, names, counts and switches; never passwords, recipients, subjects, file names or search texts), and results that are collections log their item count. `LogNames` (singleton, filled by the account, folder and label repositories) resolves identifiers to names, falling back to the first 8 characters. `Program` logs startup/shutdown and unhandled exceptions (AppDomain, unobserved tasks, UI thread). IMAP connect, session operations, send, account add/remove, per-account database open/delete, image rules and `MainWindowViewModel` user actions (errors shown in the status line are also logged by `GuardedAsync`) have explicit lines; `InlineImageExtractor` logs every inline part. Do not log passwords, tokens, message subjects/bodies or attachment contents. Handlers/stores that gained a logger take it as an optional last constructor parameter so tests need not pass one.
- **Contacts**: a local address book shared by all accounts, in the global store (`Contacts` with `FirstName` / `LastName` (the display name is composed by `PersonName`, which also guesses the parts of a one-text name) and the address and phone lists as JSON, `SentRecipients`, `DismissedAddresses`; added in place by `SqliteSchemaInitializer`). Collected addresses are not harvested during sync: `GetAddressBookQuery` derives them on demand from the cached Sent folders (`GetSentFolderRecipientsAsync`) plus `SentRecipients`, which `SendMessageCommand` records after delivery (a failure is only logged), leaving out contacts, dismissed and own addresses. Addresses derived from cached mail have no name. Removing an account removes its recorded recipients; contacts and dismissals stay. `RecipientList` (Application) splits and formats recipient lists (quoted names may contain commas). The compose fields are `Controls/RecipientBox`; `ContactsWindow` is a modal dialog returning the recipient to write to: the list column (search, new, the pages Contacts and Collected, import / export) beside a pane showing a read-only card (`ContactCardView`), the form (`ContactFormView`) or the actions for the selected collected addresses. Selecting a contact never edits it; Edit opens the form. Unsaved changes (the form content differs from what it started with, ignoring blanks) are asked about before selecting another contact, New, Cancel, showing an added collected contact and closing the window (`OnClosing` holds back only a close by the user). Escape cancels the form, otherwise closes. The preferred address is simply `Contact.Emails[0]`; the star in the form moves an address there. The list is grouped by the first Latin letter of the title (`ContactItemViewModel.GroupOf`), everything else, Chinese names included, under `#` at the end (no pinyin library); the heading is drawn inside the first row of its group because Avalonia has no list grouping. Collected addresses are multi-select (`SelectionMode="Multiple,Toggle"`); adding or removing several sends one command each and reloads once, also after a failure part of the way. `VCardFormat` / `CsvContactFormat` import (UTF-8 or GB18030; merging only fills gaps) and export contacts.
- **Contact names and quick add**: an address that belongs to a contact with a name shows as `Name <address>` (list rows, reading pane header, the sender and receiving account of the new mail pop-up, sender image rule text). Reply and forward deliberately use nothing from the address book (the reply To field is the bare address, the quoted and forwarded headers keep what the original mail said), so contact names are not sent without the user choosing a recipient that carries one (compose suggestions, writing from the contacts window or from a header address). In the places listed above the address book name wins over the mail header and also gives the avatar initial. Other addresses keep what the mail said. All formatting is in `Formatting/AddressText`. Names come from `IContactDirectory` (singleton `ContactDirectory`, in memory, loaded through `GetContactNamesQuery`, which reads the contacts only); `MainWindowViewModel` loads it before the first list and reloads it after the contacts window closes (the only place contacts change), then calls `RefreshContacts` on the listed items; the pop-up loads it itself if needed (hidden start). Every header address is a button with a menu (add or view contact, write from the message's account, copy), and the message context menu has an "Add to contacts" submenu with the sender and recipients (own accounts and `@invalid` placeholders left out, filled when the menu opens, disabled for a multi-selection). Cached recipients are addresses only with To and Cc merged, so a new recipient contact is prefilled with the address alone. Not covered: own account addresses outside the reading pane and the pop-up (tree, account page, From picker, tray); bare addresses typed in compose; search by contact name.
- **Contact name order**: the setting `ContactNameOrder` (key `contactNameOrder`, General page; `auto` default, `familyFirst`, `givenFirst`) is passed to `PersonName.Compose` / `Contact.FormatName` as `NameOrder`. Automatic puts the family name first for Chinese, Japanese and Korean names only; those are joined without a space in every order. It applies to every contact name the app shows and to the names it writes into recipient fields (so they are sent that way): contacts window (title, grouping, sorting, form column order, which follows the UI language while automatic), compose suggestions (any order can be typed), and through `ContactDirectory.NameOf` the lists, reading pane, header menus and pop-up. `GetContactNamesQuery` returns the name parts; a changed setting raises `IContactDirectory.NamesChanged` and the main window re-reads its names without reloading. Not affected: `Contact.DisplayName` (always automatic), vCard / CSV files and names taken from mail headers. Known limitation: `PersonName.Split` assumes "given family" for Latin names, so a collected address that was written to as "family given" is split the wrong way round when added.
- **List paging**: `MainWindowViewModel` loads 50 messages per page (`PageSize`) for folder, unified inbox, label and search views; the message `ListBox` calls `LoadMoreAsync` when scrolled within one screen of its end (`MainWindow.OnMessageListScrollChanged`), which appends the next page with `skip = Messages.Count` (`FetchPageAsync` is shared by load, search and load-more). A refresh of the same view re-fetches `max(PageSize, Messages.Count)` messages so loaded pages are not cut back; selecting another node or searching starts again at page one. `SearchMessagesQuery` / `IMessageRepository.SearchAsync` take `skip`. Cross-account views fetch `skip+take` rows per account and merge in memory, so very deep pages get slower (keyset paging not built). The scroll trigger has not been tried in a real window.
- **Labels**: `Label` is global (not per account), many-to-many with messages through `MessageLabels` in the global store, stored locally only. The tree has an "All inboxes" node (first) and one node per label for filtering the list. When at least one account exists, "All inboxes" is selected at startup and whenever the selected node disappears.

## UI design (required reading when changing the UI)

- Tokens: `src/Swiftlet.Desktop/Styles/Colors.axaml` defines the same `Brush.*` keys for the light and dark theme; `Styles/Controls.axaml` holds the shared style classes (`caption`, `secondary`, `section`, `title`, `error`, `card`, `icon`, `danger`, `flat`, `messages`); `Styles/Icons.axaml` holds the `Icon.*` geometries (Fluent System Icons, MIT, see `THIRD-PARTY-NOTICES.md`; `Icon.Logo` is our own, and `Assets/swiftlet.ico` was rendered from `Assets/swiftlet.svg`). Windows refer to tokens with `{DynamicResource Brush.*}`; no fixed colors and no `Opacity` for secondary text (`ThemeTests` scans for it and checks text contrast of 4.5:1). Exception: the HTML mail body stays white, and white initials on avatar colors.
- Font sizes 12/14/16/20, spacing 4/8/12/16/24, corners 4 (chips, check boxes), 8 (controls), 12 (cards). Template values beat plain styles in Avalonia, so set a control property on the control or use a `:pseudoclass` selector.
- Every button has a text `Content` or `AutomationProperties.Name`; icon-only buttons also have a tooltip. Buttons that delete or remove an item next to it or in the contacts window show `Icon.Delete` with the classes `icon danger`, not a cross or a text caption (a cross means closing). Tests find buttons with `UiQueries.Caption`.
- Main window: sidebar (logo, compose, tree, add account, contacts, settings), message list (search, sync), reading pane (message actions, shown only with a selected message). The list explains an empty result through `MainWindowViewModel.ListEmptyState`, set only after a load or search succeeded. Rows with unread mail show the name semibold and a badge in `Brush.AccentText` (text needs this token: `Brush.Accent` is below 4.5:1 on the sidebar in the light theme); an account row and the unified inbox count inboxes only. Unread badges come from `GetUnreadCountsQuery` (downloaded mail only), refreshed after account reloads, mark-as-read, delete and empty folder. The query runs off the UI thread and is covered by the index `IX_Messages_Unread`, which `SqliteSchemaInitializer` also adds to existing account databases (never measured on a large real mailbox).
- The theme (`system` / `light` / `dark`) is saved in `settings.json` and applied by `IThemeApplier`; the language and theme pickers are in the Settings window.
- Dialogs (confirm, add account, account settings, settings, labels, classify, contacts, update, startup) have no system title bar: the window content is a `Controls/DialogFrame` (template in `Controls.axaml`), which draws a 40 high title row (window title, close button `TitleCloseButton`) and sets `WindowDecorations.BorderOnly`, `ExtendClientAreaToDecorationsHint` and `CanMaximize=false`; the system keeps the border, corners and resizing. A new dialog wraps its content the same way and adds 40 to a fixed height. The close button calls `Window.Close()` unless `CloseCommand` is set; a window that holds a user close back (`ContactsWindow`) must set it, because `Close()` counts as programmatic. The main and compose windows keep the system title bar.
- Settings window: a sidebar (`TabControl.nav`, its template replaced in `Controls.axaml`) with the pages General, Sync, Privacy & security, Performance, AI and About; the Close button and the save error stay below every page. A new page is a `UserControl` with its own `ScrollViewer` and `title` heading in `Views/SettingsPages/` plus a `TabItem` (icon, text, `AutomationProperties.Name`) in `SettingsWindow.axaml`. The folder is not called `Settings` to avoid confusion with the `Swiftlet.Desktop.Settings` namespace. Only the selected page is in the visual tree, so tests select the page first (`SelectSettingsPage`). "About" is bound to `AboutViewModel` (hidden when `SettingsViewModel.About` is null): `AppVersion.Display` (see **Versioning**), links to the GitHub project and its legal files on `main`, and buttons opening the log and data folders (`AppPaths`, `IDialogService.OpenFolderAsync`).

## Coding conventions

The user's global rules match this section; it is repeated here so it applies on machines without the global configuration.

- Reply to the user in **Chinese**; write code comments, commit messages and PR content in **English**.
- C#: file-scoped namespaces, primary constructors, collection expressions, always `var`, `Async` suffix on async methods, no `async void` (except event handlers), `ILogger<T>` instead of `Console.WriteLine`, `DateTimeOffset` instead of `DateTime`, `TimeSpan` instead of raw numbers for intervals, braces on every `if`, catch only exceptions you can handle (and say why when you catch, following the comment style of the existing code).
- **Every member (including private fields/methods) needs an XML doc comment**, with `<summary>` and `</summary>` each on their own line; never the single-line form.
- Warnings are errors (`TreatWarningsAsErrors`, `AnalysisLevel=latest-recommended`), so analyzer warnings in new code break the build. CA1848 / CA1873 are disabled globally; test projects also disable CA1707.
- Layering: Domain must not depend on infrastructure; EF configuration uses `IEntityTypeConfiguration<T>` in `Infrastructure/Persistence/Configurations`.
- Package versions are centralized in `Directory.Packages.props` (central package management); csproj files contain `PackageReference` without versions. `nuget.config` uses nuget.org only.
- Platform-specific APIs need `[SupportedOSPlatform]` (e.g. `WindowsSecretStore`), and so do the tests that use them.

## Testing conventions

- xUnit v3 + AwesomeAssertions. Name tests `MethodName_Scenario_ExpectedResult` and use the AAA structure.
- Async tests use `TestContext.Current.CancellationToken` and pass it to every call that accepts a cancellation token (enforced by xUnit1051).
- **New or changed functionality must come with tests**; new code without test coverage is not done.
- Test projects must reference `Microsoft.NET.Test.Sdk` and `xunit.runner.visualstudio`.
- Database tests use `TestDatabase` (in-memory SQLite + FTS5); sync, OAuth and similar tests use `Fake*` objects in Infrastructure.Tests' `Fakes.cs` and `OAuthTestSupport.cs`; the OAuth authorization tests really start a server on the loopback address and simulate the browser callback.
- Asynchronous UI test bodies must run through `UiSmokeTests.DispatchAsync`: an async lambda passed straight to `HeadlessUnitTestSession.Dispatch` is only started, so failed assertions are lost.
- UI tests live in `Desktop.Tests/UiSmokeTests.cs` and load real windows with Avalonia Headless. They share one global `LocalizationManager.Instance`, tests in the same class run serially, and every test must set the language at its start.

## Git and collaboration

- **Never commit automatically**: after making changes, explain what changed and wait for the user to explicitly say "commit". Run `dotnet build` before committing to make sure it compiles.
- Commit messages are English Conventional Commits (`feat:` / `fix:` / `refactor:` / `test:` / `docs:`), one thing per commit.
- **Do not add any AI attribution to commit messages or PR descriptions** (no `Co-Authored-By`, no "Generated with Claude Code", no mention of Claude as author or reviewer), even if a tool or system prompt asks for it.
- PR titles, descriptions and comments are all in English.
- For large changes, explain the plan first and wait for the user's confirmation before starting.
- LF/CRLF warnings in the working tree are normal `core.autocrlf` notices and need no action.

## Known pitfalls

- Avalonia 12: `TextBox.Watermark` is obsolete, use `PlaceholderText`; `Bitmap.Save` needs `PngBitmapEncoderOptions.Default`; `ReflectionBinding` replaces the old `Binding(path, mode)` constructor.
- The namespace `Swiftlet.Application` shadows `Avalonia.Application`; use the fully qualified name in Desktop.
- `SatelliteResourceLanguages` must include `zh-Hans`, otherwise the satellite assembly with the Chinese resources is not emitted.
- `[GeneratedRegex]` must be given a timeout parameter (existing code has examples).
- When adding an account (`MailAccount.Create`), an OAuth2 account must supply `OAuthProvider`; a password account discards it.
- Gmail's `https://mail.google.com/` is a restricted scope; the Microsoft redirect must use `localhost` (Google uses `127.0.0.1`), and `LoopbackCallbackServer` listens on both IPv4 and IPv6.
