# CLAUDE.md — Swiftlet

Cross-platform email client: .NET 11 + Avalonia 12, IMAP/SMTP (MailKit 5), SQLite + FTS5, OAuth2 (Google / Microsoft), English and Simplified Chinese UI.
This file lets Claude Code pick the project up in a fresh session; it also holds the project's progress and roadmap.

## First steps when taking over

1. Run `git log --oneline` and `git status` to see where the project stands and whether anything is uncommitted.
2. Run `dotnet build Swiftlet.slnx`, then run the tests project by project (see below). The baseline is **723 passing tests** (Domain 45 / Application 66 / Infrastructure 374 / Desktop 238) with a 0-warning build.
3. Read "Remaining work" at the end of this file. **M5a (unified inbox + labels + server-side delete) and M5.5 (read/starred flag sync) are done.** **Account management (delete + OAuth re-sign-in), IMAP IDLE, history backfill, parallel sync and the immediate flag push are implemented.** The next step is not chosen yet; candidates are verifying against real providers or M6. Ask the user before starting. The rules feature and the local trash were cancelled by the user: do not build them.
4. Storage is split per account (see **Database** below). There are no EF migrations and no code that moves data out of an old single-file database: the local dev database `%LocalAppData%\Swiftlet\swiftlet.db` created by an earlier version must be deleted once and the accounts added again, otherwise the global store has the wrong schema. Inside an account database, `SqliteSchemaInitializer` still adds the column `Messages.IsFlagSyncPending` in place.

## Architecture

```
src/Swiftlet.Domain          Entities + repository interfaces. No infrastructure dependencies.
src/Swiftlet.Application     Mediator commands/queries, MailSyncService, abstractions (IImapSession, ISecretStore, IOAuthAuthorizer, ...)
src/Swiftlet.Infrastructure  EF Core/SQLite, MailKit implementations, OAuth, keychain, AccountSyncWorker, DI registration
src/Swiftlet.Desktop         Avalonia views, ViewModels, localization, dialog service, Program (host + startup)
```

Dependency direction: Desktop → Infrastructure → Application → Domain.

Key design points (understand these before changing code):

- **CQRS**: uses `Mediator` (the source-generator library, not MediatR). Commands implement `ICommand<T>`, queries implement `IQuery<T>`, handlers live in the Application layer. `AddApplication()` registers Mediator with a **Scoped** lifetime (handlers depend on scoped repositories).
- **ViewModels never use `ISender` directly**; they use `IRequestDispatcher` (`ScopedRequestDispatcher`: opens a fresh DI scope per request so long-lived ViewModels do not share a `DbContext`). It has separate overloads for commands and queries because generic inference fails on Mediator's `IRequest<T>`.
- **All external interaction in Desktop is abstracted**: `IDialogService` (windows, file pickers, opening the browser, confirmation dialogs), `IRequestDispatcher`, `ILocalizer`, `ILanguagePreferenceStore`. Tests use `FakeDispatcher` / `FakeDialogService`.
- **Sync**: `MailSyncService` fetches incrementally by UID; a UIDVALIDITY change clears that folder's cache; on first sync (no cached messages in the folder) only the newest 20 messages per folder are fetched (`MailSyncOptions.InitialFetchCount`; later syncs fetch at most `MaxMessagesPerFolderPerSync` = 200 new messages). **Parallelism**: one sync uses up to `MailSyncOptions.ConnectionsPerAccount` = 3 connections (1 = serial). Folders are queued Inbox, Sent, others, All Mail, Trash/Junk (`FolderSyncOrder`); the primary connection starts at once, additional ones (at most folders - 1) join when connected and are cancelled once the queue is empty. Repositories share one context, so **all database work and folder entity changes go through `DatabaseGate`**; only IMAP calls overlap. An additional connection that cannot be opened is a warning; one that fails on a folder stops, and the primary connection retries that folder once. **History backfill**: `BackfillWorker` (BackgroundService, up to the same number of dedicated IMAP connections per account, `BackfillConnections`; additional ones are opened when a batch first has more than one download, `ParallelDownloader` keeps one download per connection, a failing additional connection is retired and the primary one takes over its message) then downloads older mail in batches of `BackfillBatchSize` = 100 through `MailBackfillService` (`IImapSession.ListOlderAsync` lists a batch with Message-IDs from the envelope, `FetchMessagesAsync` downloads the bodies), walking back from the lowest cached UID (`IMessageRepository.GetMinUidAsync`; no stored cursor, so it resumes after a restart). Every batch runs under the account's `SyncCoordinator` lock and releases it afterwards; it **ends early when anyone waits for that lock** (`SyncCoordinator.HasWaiters`): no further downloads start, the ones running are stored and the batch reports `Progressed`. A batch checks the folder's UIDVALIDITY first and raises `AccountSynced` once per batch. **Messages are committed one by one, strictly newest UID first**, although downloads overlap (so the lowest cached UID, the resume cursor, moves down without a gap and an interrupted batch loses at most the downloads in flight, one per connection); copies from other folders are committed in runs, and each commit raises `BackfillProgressed` with the folder name and how many older messages are left (status line `Status_HistoryDownloadingFolder` in `MainWindowViewModel`). **Deduplication**: before downloading, the batch's Message-IDs are looked up in the account's other folders (`IMessageRepository.FindByMessageIdsAsync`, index `IX_Messages_MessageIdHeader`, added in place by `SqliteSchemaInitializer`); a hit is copied locally (`MailMessage.CopyToFolder`, attachment metadata included, no network) and only unknown messages are downloaded. Folder order: Inbox, Sent, other folders, then `FolderRole.AllMail` (Gmail's All Mail, from the IMAP `\All` attribute; most of it is copied, and it is skipped when `DownloadAllMail` (default on) is off), then Trash and Junk last. Search hides the All Mail row of a message that also exists in another folder (the All Mail folder view itself lists everything). Rows stay per folder (no shared-content table), so labelled mail is stored twice as text. `DownloadFullHistory` (default on, Settings window) switches the whole backfill off. A finished account is re-checked after 1 hour; a pass that fails with a transient error is repeated 3 times (5 s doubling), then retried after 5 minutes. A folder being emptied is skipped. Known limitation: `PullFlagsAsync` still fetches the flags of the whole cached UID range at every sync, which gets expensive once the history is downloaded (needs CONDSTORE `CHANGEDSINCE` or a throttled full reconcile; not built yet) `AccountSyncWorker` (a BackgroundService) checks every 30 seconds which accounts are due, using `MailAccount.SyncInterval`, and syncs the due accounts side by side; the Sync button does the same (`MainWindowViewModel.SyncAccountsAsync`).
- **Authentication**: `MailAuthentication.AuthenticateAsync` handles both password and XOAUTH2. OAuth uses the standard authorization code flow + PKCE + loopback redirect (`OAuthAuthorizer` + `LoopbackCallbackServer`), with no MSAL dependency. The client id comes from an environment variable or `%LocalAppData%\Swiftlet\oauth.json`; **no credentials are embedded in the code**.
- **Secret storage**: the platform implementation of `ISecretStore` is chosen by `PlatformSecretStore.Create`: Windows DPAPI / macOS `security` command / Linux `secret-tool`, falling back to the file-based `DataProtectionSecretStore` when none is available. Tokens are stored as JSON under the key `account:{id}:oauth`.
- **Database**: storage is split into a **global store** and **one SQLite file per account**. `GlobalDbContext` (`swiftlet.db`) holds `Accounts`, `Labels` and `MessageLabels` (`MessageId`, `LabelId`, `AccountId`; no foreign key to messages). `AccountDbContext` (`accounts\{accountId}.db`, created on first use by `IAccountDbContextFactory` / `AccountDbContextFactory`) holds `Folders`, `Messages`, `Attachments` and the FTS5 index. `AccountContextProvider` (scoped) hands every repository of a request the same `AccountDbContext` per account. Because messages are looked up per account, repository methods and commands keyed by a folder or message id take the owning `AccountId` first (`DeleteMessageCommand`, `SetMessageReadCommand`, `SetMessageFlaggedCommand`, `SetMessageLabelCommand`, `DownloadAttachmentQuery`, `GetMessagesQuery`, `IMessageRepository`, `IFolderRepository.GetAsync`). Cross-account views (unified inbox, label filter, search without an account) query each account database for its newest `skip+take` rows and merge by `SentAt` in memory (`MessageRepository`). `MailMessage.Labels` is not mapped by EF: `MessageRepository` loads the links from the global store after reading messages and `SaveLabelsAsync` writes them. Label links of deleted messages are removed best effort (orphan links are harmless). `AccountRepository.DeleteAsync` removes the account's label links and row, then deletes the account's database files. `SqliteSchemaInitializer` has `InitializeGlobalAsync` and `InitializeAccountAsync` (`EnsureCreated` plus hand-written FTS5 DDL and triggers); `Program` initializes the global store and every existing account database at startup. **There are no EF migrations**: after changing entities, delete the local `%LocalAppData%\Swiftlet\swiftlet.db` and the `accounts` directory during development, unless the initializer adds the change in place: it adds `Messages.IsFlagSyncPending` to an existing database idempotently (`pragma_table_info` + `ALTER TABLE`). All time fields are stored as Unix milliseconds (`UnixMillisecondsConverter`) so they sort correctly.
- **Search**: FTS5 trigram tokenizer; terms shorter than 3 characters fall back to `LIKE`; query terms are escaped into literals so user input is never treated as FTS syntax.
- **Attachments**: only metadata is stored locally (including `Ordinal`, the attachment's position in the server message); content is fetched from IMAP on demand via `DownloadAttachmentQuery`. Attachments are enumerated by `MimeAttachments.Enumerate` (used by both the mapper and the download, so ordinals agree): MimeKit's `Attachments` first (unchanged order), then non-text parts with a file name that are shown inline (for example a photo referenced by `cid:`). Cached messages synced before this are not backfilled.
- **Local state**: deleting is queued locally and written back to the server in the background right away. Read and starred state are applied locally at once, marked per message with `MailMessage.IsFlagSyncPending`, and written to the server in the background right away (see **Immediate flag push**); the next sync writes whatever that push could not. Labels are still local only.
- **Flag sync** (M5.5): per folder, after the UIDVALIDITY check (an invalidated folder skips both push and pull), the order is push → fetch new → pull. Push: pending messages are read as untracked `MessageFlagState` projections and sent with `IImapSession.SetFlagsAsync` (only `\Seen`/`\Flagged`; clearing is pushed too); `ClearFlagSyncPendingAsync` then clears the marker only for rows whose IsRead/IsFlagged still equal the pushed values, so a change made during the push stays pending. A failed push is a logged warning, non-fatal, and the messages stay pending, so it never blocks new mail. Pull: `IImapSession.FetchFlagsAsync(folder, minUid)` for UIDs >= the lowest cached UID; the server wins except for pending messages (the guarded `ApplyServerFlagsAsync` update skips them). Cached messages absent from the result or flagged `\Deleted` are removed locally only when `RemoveServerDeletedMessages` is on (default off), the server result is non-empty (an empty result for a non-empty cache logs a warning and removes nothing) and the folder was not just invalidated. The pull uses untracked projections and `ExecuteUpdate`, never tracked message entities.
- **Immediate flag push**: `SetMessageReadCommand` / `SetMessageFlaggedCommand` notify `FlagPushSignal` after saving. `FlagPushWorker` runs one loop per account: it waits 300 ms for further changes, then `PendingFlagService.PushFolderAsync` writes every folder with pending rows (UIDVALIDITY check, STORE, clear the matching marks). The connection is kept for 2 minutes after the last change; a push that fails on a kept connection reconnects at once, passing errors are retried 3 times, and after that the rows stay pending for the next sync. It does **not** take the `SyncCoordinator` account lock, so it does not wait for a running sync. Instead `FlagCoordinator` (per folder) is held by the push, by the sync around UIDVALIDITY invalidation + push, and around the flag pull, so flags read before a push are never applied after it.
- **Settings**: `settings.json` holds `Language` and `RemoveServerDeletedMessages` (default false), implemented by `AppSettings` in `src/Swiftlet.Desktop/Settings`, which implements `ILanguagePreferenceStore`, `ISyncSettings` and `IAppSettings`. `ISyncSettings` (Application) is read on every sync; `AddApplication()` registers an always-false default with `TryAdd`, and `AddAppSettings`, registered after it, wins. The Settings window (toolbar button) has one checkbox for this setting.
- **Account management**: right-clicking an account node in the tree opens a context menu (no prior selection needed; the commands take the node as parameter) with "Remove account" and, for OAuth accounts only (`AccountNodeViewModel.CanReauthenticate`), "Re-sign in". `DeleteAccountCommand` deletes the local rows first (account, folders, messages and their label links; the account row is the point of no return) and only then the secrets (password / OAuth tokens); the mailbox on the server is never touched, which the confirmation dialog states (Cancel is the default). `ReloadAccountsAsync` removes tree nodes of accounts that no longer exist, repairs a selection that pointed into them, and never re-inserts a node for an account that a newer reload already dropped. After a delete attempt (even a failed one) the view model reloads the tree from the database and re-runs the active search or reloads the folder view. `DeleteAccountCommand` removes both secret keys (password and OAuth) even when the account row is already gone, so a retry after a failed secret removal cleans up. `AccountSyncWorker` uses one DI scope (one `DbContext`) per account, so a failed sync of one account (for example one deleted mid-sync) cannot leave stale tracked entities that break the next account. `ReauthenticateOAuthAccountCommand` (OAuth accounts only) runs the browser sign-in, rejects a different email address (case-insensitive compare) before touching stored tokens, re-checks that the account still exists after the browser step, saves the new tokens, verifies them with an IMAP connection and restores the tokens that were stored just before the overwrite if that fails (a restore failure is logged and attached to the original exception); the view model then syncs the account. When a sync throws `OAuthReauthenticationRequiredException` (it reaches Desktop unwrapped), the status line names the account and tells the user to right-click it and choose Re-sign in.
- **IDLE / push**: `InboxWatcher` (a BackgroundService in Infrastructure) keeps one dedicated IMAP connection per account in IDLE on the INBOX, separate from the sync connections. The first wait of every session reports a change (`FolderChangeTracker.Observe` returns true for the first observation of a folder), so every (re)connect is followed by a sync, and the wait after that sync is compared against the baseline taken before it; mail that arrives during the sync is therefore caught by the next wait. `FolderChangeTracker` covers changes between waits, and the IDLE events cover changes during a wait. After an IDLE the baseline is recorded with UIDNEXT unknown (MailKit refreshes it only on SELECT), so the next comparison uses the message count only. Known limitation: a UIDNEXT-only change right after an IDLE (for example mail arrives and another client moves one out of the INBOX during the post-IDLE sync) is not detected by the tracker at all; only a later IDLE event or the polling timer recovers it (the 5-minute renewal does not sync). The reconnect backoff resets only after a wait that actually idled, not after the first wait of a session (which returns right after the SELECT), so an IDLE that fails on every connection keeps backing off. Each IDLE wait lasts at most 5 minutes (`maxWait`), after which it renews; a dropped connection is retried with a backoff of 5 seconds doubling up to 5 minutes, and an account that needs OAuth re-sign-in waits 5 minutes before the next attempt. `SyncCoordinator` serializes syncs per account, so the IDLE-triggered sync, the timer sync and the Sync button never overlap for one account. `SyncAccountCommandHandler` raises `ISyncEvents.AccountSynced` (a singleton, possibly on a background thread) after every successful sync, **and once earlier as soon as the INBOX is done** if something in it changed and the account has further folders (`MailSyncService.SyncAsync` callback; the final event reports only the messages not announced yet); `MainWindowViewModel` subscribes, marshals to the UI thread through `IUiThread` (`AvaloniaUiThread` in production) and refreshes coalesced: refreshes never overlap, and syncs arriving during a refresh cause at most one follow-up. The subscription ends when `MainWindow` closes (`Dispose`). The 30-second UI timer and the `AccountSyncWorker` timer stay as fallbacks, and servers without the IDLE capability are served by timer polling alone.
- **Server-side delete** (background): the UI only queues. `DeleteMessagesCommand` marks rows `MailMessage.IsDeletePending` (hidden from every view query, still counted by `GetMin/MaxUidAsync` so they are not downloaded again) and notifies `DeletionSignal`. `EmptyFolderCommand` (folder context menu "Delete all messages", never for All Mail) stores `MailFolder.EmptyThroughUid` = highest cached UID, so the whole server folder including undownloaded history is deleted but later mail is kept; a UIDVALIDITY change clears the request. Both columns are added in place by `SqliteSchemaInitializer`. `DeletionWorker` (signal, plus a 30 s poll for work left from the last run) runs one pass per account on one connection; `PendingDeletionService.ProcessBatchAsync` handles one folder and at most 100 messages per `SyncCoordinator` lock: UIDVALIDITY check, then `IImapSession.DeleteMessagesAsync` (one MOVE to Trash, or `\Deleted` + UID EXPUNGE inside Trash / without a Trash folder, which needs UIDPLUS); local rows change only after the server confirmed. Emptying lists server UIDs with `ListUidsBetweenAsync` and walks them oldest first, so the highest cached UID stays until the end. Transient errors retry forever (5 s doubling to 5 min); `MailOperationRejectedException` (MailKit `ImapCommandException` / `FolderNotFoundException`) and `NotSupportedException` clear the marks so the messages reappear; other errors (sign-in) pause the account 5 minutes. Progress is raised as `ISyncEvents.DeletionProgressed`. The list is multi-select (Delete key, context menu); one confirmation per action (Cancel default), then the rows leave the list at once. **Moving to Trash keeps the cached row** (same id, labels, attachments; `IMessageRepository.MoveToFolderAsync`) when the server reports the new UID, the cached Trash has the server's UIDVALIDITY and every server message between its highest cached UID and the new one is a row being moved (no hole, which the incremental sync would never fill); otherwise the row is deleted and the sync fetches it from Trash. Other folders' copies of the same message (Gmail) stay until the next sync/pull.
- **Retries** use Polly (`Polly.Core`, Infrastructure only), all defined in `Infrastructure/Resilience`: `TransientErrors` (network, timeouts, MailKit connection/protocol errors, HTTP 5xx/408/429; never authentication failures) and `RetryPipelines` (`Endless` for the deletion worker and the IDLE watcher, with a `FailureStreak` reset on success and 5 minutes for an expired sign-in; `Transient` for the limited retries). Account sync repeats twice (5 s, 10 s), backfill 3 times, OAuth token **refresh** 3 times (1 s doubling). Deliberately no automatic retry: SMTP send and Sent append (duplicates), the authorization-code exchange, the Sync button, interactive account operations, attachment downloads. The IDLE watcher retries every failure, not only transient ones.
- **Mail text encoding**: `MailEncodings.Register()` (called from `Program` and from `MimeTextDecoder`'s static constructor) registers the code pages provider so GBK / GB2312 / Big5 / Windows-125x work. `MimeMessageMapper` does not trust MimeKit's `TextBody` / `HtmlBody`: `MimeTextDecoder` decodes the part's bytes itself. A reliable declared charset is used unless the bytes are valid UTF-8 with at least two non-ASCII characters (then UTF-8 wins); undeclared, unknown or commonly mislabelled charsets (us-ascii, iso-8859-1, windows-1252) are guessed in the order UTF-8, GB18030, Big5 (Big5 text that is also valid GB18030 is read as GB18030; this is a known limitation without a detection library); HTML without a MIME charset uses its `<meta charset>`; undeclared ISO-2022-JP is recognised by its escape sequence. Raw 8-bit Subject / From headers (no RFC 2047 encoding) are decoded by the same guessing; RFC 2047 encoded words are left to MimeKit. Already cached messages are not re-decoded.
- **HTML mail rendering**: the reading pane shows `MessageItemViewModel.HtmlDocument` (built by `HtmlMailDocument`: UTF-8 meta, CSP `default-src 'none'; img-src data:; style-src 'unsafe-inline'`, white base style) in `HtmlBodyView`, a `Border` hosting Avalonia's `NativeWebView` (package `Avalonia.Controls.WebView`, MIT, WebView2 on Windows). The document is loaded once `AdapterCreated` fires; navigations to http/https/mailto links are cancelled and opened with `TopLevel.Launcher`, new-window requests are swallowed, so scripts and remote images never run. Messages without HTML keep the plain-text `SelectableTextBlock`; the toolbar "view in browser" button still exists. **Images**: remote (http/https) images are blocked by the CSP by default; when the HTML references some (`HtmlMailDocument.HasRemoteImages`) the pane shows a banner with a "Load images" button, which sets `MessageItemViewModel.AllowRemoteImages` for that message object only (not persisted) and rebuilds the document with `img-src data: https: http:` (scripts and everything else stay blocked). Images embedded in the message (`cid:`) are not stored locally: selecting a message whose HTML has `cid:` references (`InlineImageReferences.Find`) sends `GetInlineImagesQuery` once per message (`InlineImagesRequested`; a failure shows a status error and the next selection retries), which connects to IMAP only when there are references, and `InlineImageExtractor` takes png/jpeg/gif/webp/bmp parts matched by normalized Content-ID (no SVG, 10 MB per message). HEIC / HEIF parts, which the web view cannot display, and images over 2 MB (phone photos, up to 25 MB source; large GIFs are skipped) are converted to a JPEG with a side of at most 2048 px by `HeicConverter` (Magick.NET); undecodable ones are left out. Remote HEIC images are not converted. `HtmlMailDocument.Build` replaces `cid:` references with `data:` URIs. **Saved allow rules**: the banner's `SplitButton` offers "Load images" (this message only) plus "always for this sender address" / "always for this sender's domain" (`MessageItemViewModel.AlwaysAllowSenderCommand` / `AlwaysAllowDomainCommand`, saved through `MainWindowViewModel.RememberRemoteImagesAsync`). Rules are lowercase strings: with `@` an exact address rule, otherwise a domain rule that matches the domain and its subdomains (`RemoteImageRule.TryNormalize` / `Candidates` in Application). They live in the global store's table `RemoteImageRules` (`Rule`, `AddedAt`; created by `SqliteSchemaInitializer.InitializeGlobalAsync` with `CREATE TABLE IF NOT EXISTS`, so an existing `swiftlet.db` is upgraded in place) and `RemoteImageRuleStore` (singleton `IRemoteImageRules`) keeps a sorted in-memory copy loaded at startup (`Program`), so `IsAllowed(From)` on selection is a synchronous lookup with no banner flash; writes go to the database first, then memory. The Settings window lists, searches (first 200 shown, with a count), adds and removes rules. The From header can be forged, so a rule only controls privacy (the sender learning the mail was opened), never security.
- **Logging**: Serilog (`Serilog.Extensions.Hosting` + `Serilog.Sinks.File`), configured in `Desktop/Services/LogSetup.cs`: files `%LocalAppData%\Swiftlet\logs\swiftlet-YYYYMMDD[_NNN].log`, rolled daily and when a file passes 10 MB, at most 7 files kept; level Debug for `Swiftlet.*`, Information otherwise, `Microsoft.*` at Warning. Code logs through `ILogger<T>`. `LoggingBehavior` (Mediator pipeline, registered in `AddApplication`) logs every command (Information) and query (Debug) with its type name and duration, and failures as errors; it never writes the request contents (passwords, bodies). `Program` logs startup/shutdown and unhandled exceptions (AppDomain, unobserved tasks, UI thread). IMAP connect, session operations, send, account add/remove, per-account database open/delete, image rules and `MainWindowViewModel` user actions (errors shown in the status line are also logged by `GuardedAsync`) have explicit lines; `InlineImageExtractor` logs every inline part. Do not log passwords, tokens, message subjects/bodies or attachment contents. Handlers/stores that gained a logger take it as an optional last constructor parameter so tests need not pass one.
- **List paging**: `MainWindowViewModel` loads 50 messages per page (`PageSize`) for folder, unified inbox, label and search views; the message `ListBox` calls `LoadMoreAsync` when scrolled within one screen of its end (`MainWindow.OnMessageListScrollChanged`), which appends the next page with `skip = Messages.Count` (`FetchPageAsync` is shared by load, search and load-more). A refresh of the same view re-fetches `max(PageSize, Messages.Count)` messages so loaded pages are not cut back; selecting another node or searching starts again at page one. `SearchMessagesQuery` / `IMessageRepository.SearchAsync` take `skip`. Cross-account views fetch `skip+take` rows per account and merge in memory, so very deep pages get slower (keyset paging not built). The scroll trigger has not been tried in a real window.
- **Labels**: `Label` is global (not per account), many-to-many with messages through `MessageLabels` in the global store, stored locally only. The tree has an "All inboxes" node (first) and one node per label for filtering the list.

## Localization (required reading when changing the UI)

- Resources: `src/Swiftlet.Desktop/Resources/Strings.resx` (English, the default) and `Strings.zh-Hans.resx`. Keys look like `Toolbar_Compose`.
- In XAML use `{loc:Loc Key}` (namespace `xmlns:loc="using:Swiftlet.Desktop.Localization"`); in code use `_localizer["Key"]` / `_localizer.Format("Key", args)`. **The parameter/field must be named `localizer` or `_localizer`**, otherwise the scanning tests cannot see it.
- `LocalizationTests` checks that both resource files have identical keys, non-empty values and matching `{0}` placeholders; that every key used in code and XAML is defined; and that every defined key is used. When adding or removing text, change both files.
- Language is switched through `LocalizationManager.SetPreference`; status-bar text already shown in a session is not rewritten. Persistent UI that must follow the language (folder names, placeholder subjects) refreshes via `RefreshLanguage()`.

## Coding conventions

The user's global rules match this section; it is repeated here so it applies on machines without the global configuration.

- Reply to the user in **Chinese**; write code comments, commit messages and PR content in **English**.
- C#: file-scoped namespaces, primary constructors, collection expressions, always `var`, `Async` suffix on async methods, no `async void` (except event handlers), `ILogger<T>` instead of `Console.WriteLine`, `DateTimeOffset` instead of `DateTime`, `TimeSpan` instead of raw numbers for intervals, braces on every `if`, catch only exceptions you can handle (and say why when you catch, following the comment style of the existing code).
- **Every member (including private fields/methods) needs an XML doc comment**, with `<summary>` and `</summary>` each on their own line; never the single-line form.
- Warnings are errors (`TreatWarningsAsErrors`, `AnalysisLevel=latest-recommended`), so analyzer warnings in new code break the build. CA1848 / CA1873 are disabled globally; test projects also disable CA1707.
- Layering: Domain must not depend on infrastructure; EF configuration uses `IEntityTypeConfiguration<T>` in `Infrastructure/Persistence/Configurations`.
- Package versions are centralized in `Directory.Packages.props` (central package management); csproj files contain `PackageReference` without versions. `nuget.config` uses nuget.org only.
- Platform-specific APIs need `[SupportedOSPlatform]` (e.g. `WindowsSecretStore`), and so do the tests that use them.

## Testing conventions

- xUnit v3 + AwesomeAssertions. Name tests `MethodName_Scenario_ExpectedResult` and use the AAA structure.
- Async tests use `TestContext.Current.CancellationToken` and pass it to every call that accepts a cancellation token (enforced by xUnit1051).
- **New or changed functionality must come with tests**; new code without test coverage is not done.
- Test projects must reference `Microsoft.NET.Test.Sdk` and `xunit.runner.visualstudio`.
- Database tests use `TestDatabase` (in-memory SQLite + FTS5); sync, OAuth and similar tests use `Fake*` objects in Infrastructure.Tests' `Fakes.cs` and `OAuthTestSupport.cs`; the OAuth authorization tests really start a server on the loopback address and simulate the browser callback.
- UI tests live in `Desktop.Tests/UiSmokeTests.cs` and load real windows with Avalonia Headless. They share one global `LocalizationManager.Instance`, tests in the same class run serially, and every test must set the language at its start.

## Git and collaboration

- **Never commit automatically**: after making changes, explain what changed and wait for the user to explicitly say "commit". Run `dotnet build` before committing to make sure it compiles.
- Commit messages are English Conventional Commits (`feat:` / `fix:` / `refactor:` / `test:` / `docs:`), one thing per commit.
- **Do not add any AI attribution to commit messages or PR descriptions** (no `Co-Authored-By`, no "Generated with Claude Code", no mention of Claude as author or reviewer), even if a tool or system prompt asks for it.
- PR titles, descriptions and comments are all in English.
- For large changes, explain the plan first and wait for the user's confirmation before starting.
- LF/CRLF warnings in the working tree are normal `core.autocrlf` notices and need no action.

## Known pitfalls

- Avalonia 12: `TextBox.Watermark` is obsolete, use `PlaceholderText`; `Bitmap.Save` needs `PngBitmapEncoderOptions.Default`; `ReflectionBinding` replaces the old `Binding(path, mode)` constructor.
- The namespace `Swiftlet.Application` shadows `Avalonia.Application`; use the fully qualified name in Desktop.
- `SatelliteResourceLanguages` must include `zh-Hans`, otherwise the satellite assembly with the Chinese resources is not emitted.
- `[GeneratedRegex]` must be given a timeout parameter (existing code has examples).
